# Close the holes first, then prove skills

> **Note added after review (6 Nov 2026):** this report reviewed an earlier draft of `CLAUDE_CODE_PROMPT.md`. All additions it asks for have since been written into the prompt: a Phase 0B hotfix for M1-1/M1-2, a password-length decision (15 characters or a written exception), server-side logout and an `Origin` CSRF check for the cookie option, `trust proxy`, strict query schemas, `sanitizeFilter` in production, `engines: "24.x"`, an early multer + Express 5 test, bootstrap intervals, baselines (the old profiler is kept), ablation, Krippendorff's α, per-script results, non-deletable `suspected_fake` records, atomic review transitions, a hash-chained audit log, and property/invariant tests. Where this report says "the prompt does not…", read it as "the earlier draft did not…".

No. As of 6 November 2026, Modules 1 and 2 of the Digital Labour Marketplace deliver most of the features the proposal lists. They are not yet correct, secure or academically safe, and Module 3 has not been started. The audit confirmed **two Critical security holes**. First, anyone can register as an administrator (M1-1, Test C1). Second, the worker directory sends every worker's CNIC, home address, emergency contact, WhatsApp number and email to any logged-in user, including other workers (M1-2, Test C8). It also confirmed **one Critical functional bug: every voice input fails to save** because of a database enum mismatch (M2-1, Tests D1 and C14). Module 2 is a hand-written keyword dictionary labelled "AI". It overwrites the worker's Module 1 data, wipes whole profiles on harmless text, matches Urdu words inside other words, and shows "confidence" percentages produced by the formula `84 + 5 × matches`. That collides directly with the department's reported warning against "AI features on top". The design positions already written into `CLAUDE_CODE_PROMPT.md` mostly match current official documentation and OWASP guidance: Express 5.3 with patched Mongoose 9, Zod validation, Vitest-based tests, a suggestion-only rule-based extractor measured with precision and recall, private image-only evidence, a keyed-hash-only CNIC, HttpOnly cookies, and a Beta/subjective-logic skill confidence. This report still finds about a dozen places where the evidence asks for more. The most important are the password length (OWASP asks for 15 characters without MFA), server-side logout, Express's `trust proxy` setting on Vercel, a loophole that lets a worker delete a "suspected fake" rejection, an unverified multer and Express 5 pairing, and missing baselines and bootstrap intervals in the evaluation plan. For a three-student FYP, the academic case for Modules 1–3 rests on measurement, not on any AI label: a frozen, double-labelled trilingual test set, and an explainable evidence model with a sensitivity analysis. All testing was offline (no real server, database or browser test was run, and the live deployment is unverified). **None of the designs in this report or in the prompt has been approved by the supervisor or the department.**

**The two Critical holes share one root cause: the server trusts whatever the browser sends and sends back whatever it has.** In M1-1 the role arrives in the request body and is accepted as-is. OWASP's Mass Assignment Cheat Sheet says to accept only "dedicated input objects… containing only fields the caller may edit" and to "explicitly allow-list fields" ([OWASP Mass Assignment](https://cheatsheetseries.owasp.org/cheatsheets/Mass_Assignment_Cheat_Sheet.html)). The OWASP Authorization Cheat Sheet adds deny-by-default and server-side enforcement ([OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)). The same codebase already does the right thing elsewhere: `updateWorkerProfile` picks out named fields instead of saving `req.body`. M1-2 is a data-minimisation failure. NIST SP 800-122 says organisations "should minimize the use, collection, and retention of PII" (personally identifiable information) and should use role-based least privilege ([NIST SP 800-122](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-122.pdf)). Reading `getAllWorkers` shows the leak in two places: the query has no field projection, and it calls `.populate('user', 'name email phone role')`, which attaches every worker's email. Because anyone could have registered as admin while M1-1 was open, the prompt's read-only `listAdmins` check against the real database is necessary, not optional.

**The two injection bugs (M1-3, M1-4) show why switching to Express 5 alone is not a fix.** *NoSQL operator injection* means a user smuggles a MongoDB operator such as `$ne` ("not equal") into a filter so that it matches records it should not. Express 5's default query parser changed from "extended" to "simple" and no longer builds nested objects from `?a[b]=c` ([Express v5 migration](https://expressjs.com/en/guide/migrating-5/)), so C7's exact attack would fail there. But repeated keys such as `?category=a&category=b` still produce arrays, and Mongoose documents that "if you forget to put `$in` on a non-array field, Mongoose will add `$in` for you" ([Mongoose query casting](https://mongoosejs.com/docs/tutorials/query_casting.html)). OWASP states that "building a query object does not prevent operator injection when an untrusted value is itself an object" and asks for a type check before any filter is built ([OWASP NoSQL Security](https://cheatsheetseries.owasp.org/cheatsheets/NoSQL_Security_Cheat_Sheet.html)). The fix therefore has three layers:

1. A validation schema that accepts only strings from known values.
2. Mongoose's `sanitizeFilter`, which is "`false` by default" ([Mongoose API](https://mongoosejs.com/docs/api/mongoose.html)).
3. Escaping any text placed in a regular expression.

`RegExp.escape()` is "Baseline 2025" in browsers ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/RegExp/escape)), but the research did not confirm which Node version ships it. The one-line manual escape is the safe choice.

**Validation and error handling (M1-5, M1-6, M1-7) follow OWASP almost word for word.** Validate on the server even when the browser already checks, enforce type, length and range, and use allow-lists ([OWASP Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)). Return "generic error messages" with no internal details ([OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)). Vercel's own Express guide warns that Express "will swallow errors that can put the main function into an undefined state unless properly handled" ([Express on Vercel](https://vercel.com/docs/frameworks/backend/express)). That is one more reason for a central error handler.

**M1-8 is the "birthday problem".** It is the same maths that makes two people in a class of 23 likely to share a birthday. With only 9,000 possible IDs, a clash becomes a coin flip at about 112 workers. Test C19's simulation agrees with the exact calculation. A database counter that increases by one atomically (in one indivisible step) cannot clash, and it also removes the hard-coded year.

**Authentication hardening (M1-10, M1-11, M1-12) is about attacks the current code cannot see.** jsonwebtoken 9 already removed the old "accept the `none` algorithm" default (CVE-2022-23540) ([GitHub advisory](https://github.com/auth0/node-jsonwebtoken/security/advisories/GHSA-qwph-4952-7xr6)). OWASP still says to "hardcode the accepted algorithms" and to use an HMAC secret of at least 256 bits for HS256, generated randomly and never a password ([OWASP JWT](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)). The 7-day token in `localStorage` goes against OWASP's current Session Management guidance (see the stack section below). The database connection should follow the official serverless pattern: cache the connection *promise* at module scope, set `serverSelectionTimeoutMS` ([Mongoose with Lambda](https://mongoosejs.com/docs/lambda.html)), and set `maxIdleTimeMS` to 60000 ([MongoDB Atlas](https://www.mongodb.com/docs/atlas/manage-connections-aws-lambda/)).

Several things are already done well and should be kept: bcrypt password hashing, role checks enforced on the backend (not only in React), named-field destructuring in `updateWorkerProfile` (which blocks mass assignment of `verificationStatus`), the serverless connection-reuse idea, and not committing `.env`.

The defects fall into five patterns, and the patterns matter more than the individual bugs:

- **The system writes conclusions instead of offering suggestions** (M2-2, M2-3, M2-9, M2-10). Every analysis replaces stored data.
- **Matching is too loose** (M2-5, M2-6, M2-12, M2-14). Substrings and ambiguous everyday words are treated as evidence of a trade.
- **Parsing is fragile** (M2-4, M2-7, M2-11). The negative filter, the year regex and type handling break on ordinary input.
- **The numbers have no basis** (M2-8, M2-15). The percentages look like probabilities but have never been measured.
- **The voice path depends on an outside service without consent** (M2-13).

Against the proposal's five Module 2 bullets, everything is "done" in form: collection, assisted identification, organisation by category, a structured profile, and suggested skills. But each bullet carries one of these defects, and calling the result "AI" invites exactly the criticism the department is reported to have made.

### Suggest, never overwrite: how the redesign removes each root cause

The prompt's Module 2 redesign (Part C5) addresses each pattern directly:

- **Suggestion-only extraction.** The extract endpoint saves nothing and returns a *suggestion object*. The worker ticks the skills they agree with, and occupation, category and years enter the Module 1 form only after a "Use these suggestions" click. That fixes M2-2, M2-3 and M2-9, and a single `skills` array with taxonomy IDs fixes M2-10.
- **Normalisation before matching.** Unicode normalisation, Urdu and Arabic digit conversion, letter-variant unification, and whole-token matching in every script fix M2-5.
- **Strong and weak terms.** Each skill has "strong" terms (clear trade words) and "weak" terms (ambiguous words such as "light", "fan", "tap", "router"). A weak term counts only when a strong term from the same category is also present, which fixes M2-6.
- **Better year parsing.** Unicode-aware boundaries, number words in three languages, months, and values above 60 flagged rather than capped fix M2-7.
- **A safer negative filter.** Negative phrases matter only when nothing matched and never delete anything, which fixes M2-4.
- **Honest output.** Matched words are returned as the explanation instead of a percentage (M2-8), and ties are reported rather than hidden (M2-12).
- **Shared taxonomy.** One taxonomy file that includes domestic work fixes M1-16 and M2-14.
- **Voice as an option.** Voice input stays optional behind a notice, with text as the main input (M2-13).
- **Honest naming.** The rename to "Skill Profiler (rule-based)" or "Skill Finder", and removing "AI" from database values, settles the labelling problem.

These choices are justified. One trade-off should be stated openly: the weak-term rule buys precision at the cost of recall. A sentence such as "I install fans and lights" contains only weak terms and would now produce no skill. That cost should be measured on the development set, not assumed away.

The taxonomy can be anchored to official codes without copying anything that is restricted:

- Pakistan's occupation classification lists 7411 building electricians, 7126 plumbers and pipe fitters, 7127 air-conditioning and refrigeration mechanics, 7131 painters and 9111 domestic cleaners ([PBS PSCO](https://www.pbs.gov.pk/sites/default/files/labour_force/publications/lfs2020_21/Pakistan_Standard_Classification_of_Occupation.pdf)). These codes match ISCO-08 numbering, although the PBS document does not say it is derived from ISCO.
- ESCO maps "each occupation… to exactly one ISCO-08 code" ([ESCO occupations](https://esco.ec.europa.eu/en/classification/occupation-main)). It may be reused free of charge for any purpose with attribution ([ESCO reuse terms](https://esco.ec.europa.eu/fr/node/173)), but it has **no Urdu labels** ([ESCO v1.2 launch](https://esco.ec.europa.eu/system/files/2024-05/V1.2%20Launch%20-%20ESCO%20SEC%20combined%20-%20final%20clean.pdf)).
- NAVTTC's competency standards, such as "Install domestic wiring" in the Level 2 electrical qualification ([NVQF qualification 15](https://web.nvqf.pk/qualification/15)), are the most local skill references. But their pages say "All rights reserved" ([NAVTTC](https://navttc.gov.pk/?p=18)), so the team should cite and paraphrase them, not bulk-copy them.

### The literature offers a baseline and a gap, not a target score

Published skill extraction work is almost entirely about English or European job postings. The main survey explicitly **excludes rule-based n-gram matching** from its scope because such methods lack "defined skill spans or labels" ([Senger et al. 2024](https://www.arxiv.org/pdf/2402.05617)). The closest published baseline for a dictionary extractor is the exact ESCO matching run by Zhang et al. on the SkillSpan job-ad dataset. It scored **strict F1 5.62 and loose F1 13.79** ([Zhang et al. 2022](https://arxiv.org/pdf/2209.08071)), while supervised models reached about 56–64 span-F1 ([SkillSpan, NAACL 2022](https://aclanthology.org/2022.naacl-main.366)). Large language models used with in-context examples were found "not being on par with traditional supervised models" ([Nguyen et al. 2024](https://aclanthology.org/2024.nlp4hr-1.3)). That supports the team's no-external-AI choice on technical grounds as well as on department grounds.

Roman Urdu is especially hard because it has no standard spelling. Pakistani SMS data shows **"each script word averages 4.2 romanizations"** ([Irvine et al. 2012](https://www.seas.upenn.edu/~ccb/publications/pakistani-SMS-corpus.pdf)), and clustering-based normalisation has been published for it ([Khan et al. 2022](https://www.cambridge.org/core/journals/natural-language-engineering/article/clustering-framework-for-lexical-normalization-of-roman-urdu/6A452B72C96AD593717749FA4B44668A)). The research found **no published work on extracting skills or occupations from Roman Urdu or Urdu worker text**. The report should state this as "to the best of our search", with the queries and dates recorded. That gap is the honest research question: how well does a curated, trade-restricted, trilingual lexicon with normalisation perform on informal worker self-descriptions, compared with naive matching? Because the domain is narrow, higher scores than the open-domain baseline are plausible. No published number supports any specific expected F1, so the report must not predict one.

### Precision, recall, Wilson and kappa are the right tools, with four additions

The prompt's evaluation plan uses standard tools. In simple terms:

- **Precision** is the share of suggested skills that are correct.
- **Recall** is the share of the correct skills that were suggested.
- **F1** is their harmonic mean (a combined score that is high only when both are high).

Because the output is a *set of skill IDs per description*, this is document-level multi-label scoring, reported per skill and as micro- and macro-averages. *Micro* pools all decisions together. *Macro* averages the per-skill scores, so rare skills count equally.

**Wilson intervals** are the right error bars for precision and recall on small samples. Brown, Cai and DasGupta showed that the usual Wald interval has "chaotic coverage properties" and recommended Wilson or Jeffreys for small n ([Brown et al. 2001](https://www.doi.org/10.1214/SS/1009213286)). A made-up illustration (not a project result) shows why sample size matters. If 45 of 50 suggestions were correct, precision would be 0.90, but the 95% Wilson interval would run from about 0.79 to 0.96. With 180 of 200 correct, the same 0.90 would narrow to about 0.85–0.93.

**Cohen's kappa** measures how much two labellers agree beyond what chance alone would produce: 1 is perfect agreement and 0 is chance level ([Cohen 1960](https://www.scilit.net/publications/7556dd9ea2d544269b6ab8862ac87cb3); the author name should be confirmed at the DOI). The usual Landis and Koch bands (0.61–0.80 "substantial") come with the authors' own warning that the divisions "are clearly arbitrary" ([Landis & Koch 1977](https://pubmed.ncbi.nlm.nih.gov/843571/)). SkillSpan's three annotators reached a final agreement of 0.70–0.75, which is a realistic reference point ([SkillSpan](https://aclanthology.org/2022.naacl-main.366)). The prompt's other rules are also supported by the literature: freeze the test set before changing rules, label independently, and include a labeller who did not write the rules. Artstein and Poesio insist that coders "work independently" and that discussing judgments makes the data unusable for measuring reproducibility ([Artstein & Poesio 2008](https://aclanthology.org/J08-4004/)).

The evidence asks for four additions to the prompt's harness. First, **F1 is not a simple proportion, so a Wilson interval does not apply to it**. The notes recommend a bootstrap interval that resamples whole descriptions, which also accounts for several skills coming from the same sentence. Second, the plan has **no baselines**. A score means little without comparison, and the old `aiSkillProfiler.js` is a ready-made baseline, alongside naive English-only exact matching. Comparisons between systems should use a paired significance test ([Berg-Kirkpatrick et al. 2012](https://aclanthology.org/D12-1091/); [Dror et al. 2018](https://aclanthology.org/P18-1128/)). Running "lexicon only", then "plus normalisation", then "plus Urdu-script lookup" turns the evaluation into an ablation study, which is a measurable non-AI contribution. Third, Artstein and Poesio recommend "a single-distribution coefficient like π or α" for reliability ([Artstein & Poesio 2008](https://aclanthology.org/J08-4004/)), so `agreement.js` should report Krippendorff's α next to kappa. It is cheap to add and answers an examiner's likely question. Fourth, results should be **broken down by script** (English, Roman Urdu, Urdu, mixed), because difficulty is likely to differ. Collecting real worker descriptions also needs informed consent and anonymisation. SZABIST's ethics requirements were not checked in this research.

### Express 5, patched Mongoose and Node 24 are the supported path, and B1 already points there

The lockfile already records Express 5.3.0 and Mongoose 9.11.2, so someone's laptop has probably already run the newer stack. Fixing B1 therefore means making `package.json` agree with a version that is already partly in use, not starting a risky jump. The security case is concrete. Express 5.3.0 carries fixes for three qs CVEs, a Critical proxy-addr IP-spoofing CVE (CVE-2026-90711) and a body-parser limit bug ([Express v5.3.0](https://github.com/expressjs/express/releases/tag/v5.3.0); [Sept 2026 security release](https://expressjs.com/en/blog/2026-09-30-security-releases/)). The October 2026 body-parser gzip crash affects the 1.x line that Express 4 uses ([Express blog](https://expressjs.com/en/blog/2026-10-28-cve-2026-111181/)). Express 5 also forwards rejected promises to the error handler automatically ([Express v5 migration](https://expressjs.com/en/guide/migrating-5/)), which removes a class of "the request hangs" bugs.

The same migration guide names the real risk in this code: `req.body` is now `undefined` when no body was sent. Reading `analyzeWorkerSkills` shows that it destructures `req.body` directly, so under Express 5 a body-less POST throws, and today's catch block turns that into a 500. The prompt's Phase 2 test ("a request with no body to a POST route returns 400, not 500") targets exactly this.

On Mongoose, 9.11.4's fix that "connection-level `sanitizeFilter` is now respected in queries" ([Mongoose releases](https://github.com/Automattic/mongoose/releases)) is the reason for the minimum version. The prompt's wording suggests enabling `sanitizeFilter` only "for development/tests". It should be on **in production as well**. Only `strictQuery: 'throw'` is a development aid.

### Cookies beat localStorage, but only with CSRF defences and server-side logout

*XSS (cross-site scripting)* means malicious JavaScript running inside our page. Any such script can read `localStorage`, which is why OWASP now says not to keep tokens there. An *HttpOnly cookie* is sent automatically by the browser but cannot be read by page JavaScript, so Option A removes token theft by XSS. It introduces a different risk. *CSRF (cross-site request forgery)* is a trick where another website makes the user's browser send a request to our API with our cookie attached. The evidence notes point out that the current Bearer-header design has low CSRF risk exactly because browsers do not attach that header on their own. Moving to cookies is a trade, not a free win.

The evidence supports Option A with three additions:

1. **SameSite=Strict**, which OWASP prefers. Because the cookie is used only by same-origin API calls, Strict should not break the app, but test it.
2. **A real CSRF control** on POST, PUT, PATCH and DELETE, such as a strict `Origin` check against the allow-list or a CSRF token, because SameSite is "defence in depth, not the only CSRF control" ([OWASP Node.js](https://cheatsheetseries.owasp.org/cheatsheets/Nodejs_Security_Cheat_Sheet.html)).
3. **Server-side invalidation at logout.** OWASP's REST sheet says to deny-list the token's `jti` (its unique ID) until expiry ([OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)). A `tokenVersion` counter on the User document does the same job for a small app.

The same OWASP sheet asks to validate `iss`, `aud` and `exp`, and the Authentication sheet asks for similar response timing on success and failure. Running a dummy bcrypt comparison when the email is not found achieves this. The same-origin Vercel rewrite at the heart of Option A has not been tested, so build it on a Preview deployment first. If it fails, Option B with a one-hour token and a frontend CSP is an honest documented limitation, not a failure.

### Storing only a keyed hash of the CNIC is the data-minimisation answer

A *CNIC* is the 13-digit Pakistani national identity number. An *HMAC* is a one-way fingerprint computed with a secret key. The same CNIC always gives the same fingerprint, so a unique index can stop one CNIC being used for two accounts, but nobody without the key can compute or check fingerprints.

Option 1 stores only that fingerprint. The admin checks identity by looking at the real card in person or on a video call and typing the number, and the server compares the hashes. This is the strongest form of data minimisation the evidence supports:

- OWASP calls not storing sensitive data "the best way to protect" it ([OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)).
- NIST tells organisations to collect PII only "where such collections are essential" ([NIST SP 800-122](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-122.pdf)).
- NADRA has advised citizens to "avoid unnecessary photocopies" of CNICs ([ARY News](https://arynews.tv/nadra-issues-advisory-on-essential-documents-photocopies/)).

The legal background points the same way without giving a compliance checklist. PECA 2016 section 16 punishes anyone who "obtains, sells, possesses, transmits or uses another person's identity information without authorization" with up to three years in prison and/or a PKR 5 million fine ([KP CERC](https://kpcerc.kpitb.gov.pk/node/229)). Pakistan's Personal Data Protection Bill "has not passed both houses of Parliament and is not enforceable" as of October 2026 ([PAKCEC](https://pakcec.com/data-protection-law-pakistan/)), although the draft treats the CNIC as sensitive data ([DLA Piper](https://www.dlapiperdataprotection.com/index.html?t=law&c=PK)). MongoDB Atlas free clusters cannot use customer-managed encryption at rest ([Atlas limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/)), so protection has to happen in the application. The report should say the design *follows* these sources, obtains consent and states the purpose. It should not claim legal compliance.

One point needs explicit handling (this is this report's analysis, not a cited finding). Thirteen digits is a small enough space that an attacker who steals both the database **and** `CNIC_HASH_KEY` could compute the HMAC of every possible number and recover all CNICs. A stolen database alone reveals nothing. So the key must be kept apart from the database and treated like an encryption key. Keeping keys in Vercel environment variables conflicts with OWASP's preference for a key-management service, and should be recorded as an accepted limitation. Option 2 (AES-256-GCM encryption plus the same hash, with a masked display and an audited reveal) adds the ability to read the number back. The price is a second key whose loss makes the data unreadable, and more code to explain in the viva.

### Fix the two Critical holes before the refactor, not in Phase 3

The prompt schedules the M1-1 and M1-2 fixes for Phase 3, after dependency, tooling and foundation work. If the live site holds real worker data, an attacker can register as admin and download CNICs during all of that time. The live deployment is unverified, so this is a conditional recommendation. With the team's explicit yes (the prompt's rules require it for pushing and deploying), make a two-change hotfix on the baseline branch:

1. Ignore any role other than `worker` or `customer` at registration.
2. Give the directory an explicit safe field list, with no email, and remove `'worker'` from its allowed roles.

Then add one regression test for each change and run the read-only admin listing against the real database.

Two smaller items should be checked early rather than discovered late. First, **no official statement says multer 2.x supports Express 5**. The Express site lists multer v2.5.0 among its middleware ([Express multer page](https://expressjs.com/en/resources/middleware/multer.html)), while a maintainer wrote in 2024 that multer still needed to be "ready to support v5" ([multer issue #1245](https://www.github.com/expressjs/multer/issues/1245)). A one-file upload test in Phase 1 settles this cheaply. Second, sharp installs different native binaries on Windows and Linux, and sharing a lockfile across platforms can cause install problems ([sharp installation](https://sharp.pixelplumbing.com/install)). The prompt's "let Vercel run `npm install`" instruction is correct.

## Module 3 should turn "Verified" into a traceable evidence trail

Module 3 replaces the M1-9 toggle with something an examiner can audit. Workers upload images of certificates, work and reference letters for specific skills. Admins approve or reject them with reasons. Each skill's verification status is then *computed* from approved evidence, never set by hand.

### Recognition of prior learning tells Module 3 what counts as evidence

The International Labour Organization defines *recognition of prior learning* (RPL) as "a process of identifying, documenting, assessing and certifying formal, non-formal and informal learning outcomes". It lists past certificates, documentation of outputs from previous jobs, and photo portfolios as evidence, and names "any worker in the informal economy" as a beneficiary ([ILO RPL Learning Package](https://www.ilo.org/publications/recognition-prior-learning-rpl-learning-package)). Pakistan runs RPL through NAVTTC under the NVQF for informal workers trained in the Ustad-Shagird system ([TVET Reform](https://tvetreform.org.pk/rpl/)), and its National Skills Passport "is linked with the Recognition of Prior Learning platform" ([ILO news](https://www.ilo.org/resource/news/empowering-migrant-workers-through-national-skills-passport-initiative)). Studies of online labour platforms explain why this matters for new workers:

- Verified, standardised work history raises hiring ([Agrawal et al. 2016](https://econpapers.repec.org/RePEc:eee:inecon:v:103:y:2016:i:c:p:1-12)).
- Early hiring and detailed evaluations improve later employment ([Pallais 2014](https://econpapers.repec.org/RePEc:aea:aecrev:v:104:y:2014:i:11:p:3565-99)).
- Microcredentials raise earnings through "decreased employer uncertainty" ([Kässi & Lehdonvirta 2024](https://jhr.uwpress.org/node/11996)).

These were global online freelancing platforms, not local in-person trades in Pakistan, so applying them here is an assumption to state. The ILO's warning applies directly to the admin review queue: "credibility and confidence in an RPL system relies on the quality of the assessment". The report should describe the admin's checking procedure and must not assume that uploaded documents are true.

### Every upload passes a sequence of checks before anything is stored

The prompt's upload pipeline maps closely onto the OWASP File Upload Cheat Sheet, which calls for:

- extension and type allow-lists,
- distrust of the browser's Content-Type,
- checking the file's real signature,
- server-generated file names and size limits,
- serving files through an ID-based handler,
- re-encoding images while stripping metadata,
- authorization on every file access ([OWASP File Upload](https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/File_Upload_Cheat_Sheet.md)).

In order, the prompt's pipeline does the following:

1. **Parse the upload safely.** multer `^2.5.0` runs with `memoryStorage`, attached only to the upload route ("never add multer as a global middleware" ([Express multer page](https://expressjs.com/en/resources/middleware/multer.html))), with a 4 MB file limit and a **synchronous** file filter. That choice is grounded in CVE-2026-113872, where "applications using a synchronous `fileFilter` are not affected" ([Express Oct 2026 security release](https://expressjs.com/en/blog/2026-10-31-security-releases)), and in CVE-2026-77063, where the size limit can be bypassed with an async filter ([Aug 2026 release](https://expressjs.com/en/blog/2026-08-31-security-releases)).
2. **Check the real type.** `file-type` ≥ 21.3.1 (the version that fixed the CVE-2026-31808 infinite-loop bug ([GitLab advisory](https://advisories.gitlab.com/npm/file-type/CVE-2026-31808/))) reads the file's *magic bytes* (the first bytes that identify its real format) and allows only JPEG, PNG and WebP. Its own documentation calls the result "a best-effort hint" ([file-type readme](https://cdn.jsdelivr.net/npm/file-type@22.0.2/readme.md)), which is why the next step matters.
3. **Re-encode the image.** sharp rotates the image correctly, resizes it to fit inside 2000 × 2000 and writes WebP. sharp's documentation states that "by default all metadata will be removed", so EXIF (hidden photo metadata that can include GPS location) is stripped ([sharp output](https://sharp.pixelplumbing.com/api-output)). The exact auto-orient method and pixel-limit option names were not verified, and the prompt rightly tells Claude Code to check them.
4. **Detect exact duplicates.** A SHA-256 fingerprint of the original bytes catches the same file uploaded twice (409 for the same worker and skill; a warning flag, not an automatic rejection, when it comes from a different worker).
5. **Respect platform limits.** The 4 MB limit leaves headroom under Vercel's **4.5 MB request-body ceiling** ([Vercel Functions limits](https://vercel.com/docs/functions/limitations)), and browser-side shrinking with `<canvas>` handles large phone photos.
6. **Serve files privately.** Files go only to the owner and admins, with an ownership check inside the route handler and `Cache-Control: private, no-store` and `nosniff` headers, as Vercel's private-storage guide recommends ([Vercel private storage](https://vercel.com/docs/vercel-blob/private-storage.md)).

**Images only, no PDF, is the right call for this version.** OWASP says PDFs need *content disarm and reconstruction* (rebuilding a document so that hidden active content is removed), and the research found no free Node tool that does it. Workers can photograph certificates instead. HEIC photos are rejected with a clear message, because file-type detects HEIC but sharp's ability to decode it was not verified. There is no antivirus scanning, and the report should list that as a limitation, with re-encoding as the realistic mitigation. The optional perceptual-hash check (dHash) is correctly marked as provisional. Published work shows that thresholds depend on the dataset ([PHASER](https://www.napier.ac.uk/-/media/worktribe/output-3529207/phaser-perceptual-hashing-algorithms-evaluation-and-results-an-open-source-forensic.ashx)), and imperceptible changes evaded perceptual hashes on ">99.9% of images" ([Jain et al., USENIX Security 2022](https://arxiv.org/pdf/2106.09820)). A match should only ever raise a flag for the admin.

### MongoDB storage is defensible, but it was not the researcher's first choice

This is the one design position where the research notes and the prompt disagree. The storage research ranked a private Vercel Blob store first and MongoDB second. The prompt reverses that order.

*BinData* is MongoDB's type for raw bytes stored inside an ordinary document. The prompt's reasons for using it hold up for a three-student team: no new service or token, offline tests that behave like production, and privacy by design. The interface it specifies (`save`, `read`, `remove` in one storage file) keeps a later switch to Blob cheap. The quota needs real numbers, though. The notes estimate (unmeasured) about 300 KB per re-encoded image. At the prompt's cap of 30 items per worker that is about 9 MB per fully active worker, so **roughly 50 heavy users would fill the free cluster**. That is fine for a demonstration, but it should be stated in the report and watched during testing. Vercel's Hobby plan is for "non-commercial, personal use only" ([Vercel Hobby](https://vercel.com/docs/plans/hobby)), which is another limitation to declare.

### A server-enforced review state machine with an append-only log

A *state machine* is a fixed set of allowed status changes. Evidence goes `pending → approved` or `pending → rejected` (a reason code is required to reject), and an admin may later move `approved → revoked` with a reason. Every change is written to an *append-only* audit log, meaning one with no update or delete routes. This follows OWASP's logging guidance: log "actions by administrators… including all of their actions" and "file uploads", record who, when, what and why, and never log "government identifiers" in plain form ([OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)).

The evidence suggests three additions:

1. **Make each transition atomic.** Update the record only if its status is still `pending` (a conditional `findOneAndUpdate`, using `returnDocument: 'after'` because Mongoose 9 deprecates `new` ([Mongoose 9 migration](https://mongoosejs.com/docs/migrating_to_9.html))). Two admins or a stale screen then get a 409 instead of double-reviewing.
2. **Add a hash chain to the audit log.** Each entry stores a hash of the previous entry plus its own content. This is a cheap answer to OWASP's "build in tamper detection".
3. **Record separation of duties as a limit.** NIST AC-5 describes separation of duties as dividing functions among different people "to reduce the risk of malevolent activity without collusion" ([NIST SP 800-53 AC-5](https://www.stigviewer.com/controls/nist-800-53/AC-5)). A three-person team will have one demo admin, so two-person approval should be recorded as future work rather than built.

Identity verification stays separate from skill verification. The admin sets the identity status with a note after an offline CNIC check, and no CNIC images are ever uploaded. The customer directory shows "Identity verified" apart from per-skill badges, which also fixes M1-9's misleading "verified workers" page title.

### The confidence score is the Beta Reputation expectation with explicit uncertainty

The *Beta Reputation System* turns counts of positive evidence `r` and negative evidence `s` into an expected score `(r+1)/(r+s+2)` ([Jøsang & Ismail 2002](https://mn.uio.no/ifi/english/people/aca/josang/publications/ji2002-bled.pdf)). *Subjective logic* splits the same evidence into three parts that always add up to 1:

- **belief** `b = r/(r+s+W)`: the share of the evidence that supports the skill,
- **disbelief** `d = s/(r+s+W)`: the share that counts against it,
- **uncertainty** `u = W/(r+s+W)`: the share reserved for "we do not know yet".

The projected score is `b + a·u` ([Jøsang 2013 draft](https://www.openphilanthropy.org/wp-content/uploads/Josang2013.pdf); [Jøsang, *Subjective Logic*, Springer 2016](https://link.springer.com/doi/10.1007/978-3-319-42337-1)). W is "normally set to W=2", which makes the starting point a uniform prior when the base rate `a = ½`. With W = 2 and a = ½, the projected score equals the Beta Reputation expectation exactly ([Jøsang & Bhuiyan 2008](https://core.ac.uk/download/10887906.pdf)). So the prompt's model is published mathematics, not an invention. The research notes warn that these formulas were read from PDFs with garbled equations and **must be checked against the original papers** before they are quoted in the report. The *weights* (certificate 2, work photo 1, reference letter 1, other 0.5) come from no published source. The prompt correctly labels them as provisional design parameters and plans a sensitivity script to test how much the results depend on them.

The table shows what the formulas produce. These are formula outputs, not measured results. The status column assumes that "Disputed" takes priority over "Verified" when both apply.

| Evidence on one skill | r | s | belief | disbelief | uncertainty | expected | Status shown |
|---|---|---|---|---|---|---|---|
| None (self-declared only) | 0 | 0 | 0.00 | 0.00 | 1.00 | 0.50 | Self-declared |
| One approved "other" item | 0.5 | 0 | 0.20 | 0.00 | 0.80 | 0.60 | Verified by evidence |
| One approved work photo | 1 | 0 | 0.33 | 0.00 | 0.67 | 0.67 | Verified by evidence |
| One approved certificate | 2 | 0 | 0.50 | 0.00 | 0.50 | 0.75 | Verified by evidence |
| Five approved work photos | 5 | 0 | 0.71 | 0.00 | 0.29 | 0.86 | Verified by evidence |
| One suspected fake, nothing else | 0 | 1 | 0.00 | 0.33 | 0.67 | 0.33 | Disputed |
| Approved certificate + one suspected fake | 2 | 1 | 0.40 | 0.20 | 0.40 | 0.60 | Disputed |

Three of the prompt's rules are well justified:

- **Self-claims add nothing.** Cumulative fusion in subjective logic assumes independent sources ([Jøsang & Bhuiyan 2008](https://core.ac.uk/download/10887906.pdf)). A typed claim and an extractor-confirmed claim both come from the worker, so counting them would double-count one statement.
- **Only `suspected_fake` counts against a worker.** A blurry or wrong-skill photo says something about the photo, not about the worker's skill. Missing evidence therefore shows up as high uncertainty, not as disbelief.
- **Missing evidence is not negative evidence.** This is a fairness choice, and the literature supports it. Women's self-evaluations ran lower than men's on male-typed tasks ([Exley & Kessler 2022](https://econpapers.repec.org/RePEc:oup:qjecon:v:137:y:2022:i:3:p:1345-1381.)). Pakistani RPL access faces barriers for women and rural workers ([Dawn, Jan 2025](https://www.dawn.com/news/1884873/empowering-workers)). Customer ratings on gig platforms correlate with perceived race and gender ([Hannák et al. 2017](https://khoury.northeastern.edu/home/amislove/publications/Freelance-CSCW.pdf)). Every evidence type can carry bias, so no missing type should lower a worker's score.

### Three loopholes in the evidence rules need closing

The first loophole is a real bug in the prompt's design. Workers may delete their own *rejected* evidence, and the score is recomputed after deletion. **A worker whose upload was rejected as `suspected_fake` could delete it, removing `s` and the "Disputed" status.** The fix: never allow workers to delete `suspected_fake` records. To respect deletion and retention wishes, delete the file bytes but keep the evidence record and its rejection, so it still counts.

The second is that **negative evidence is not weighted by type**. A fake certificate would have earned +2 if approved, but costs only 1 when caught. A worker with one approved certificate and one fake one still scores 0.60, above the 0.50 of someone with no evidence at all. The "Disputed" label softens this. Still, the evidence notes' version of the model weights negatives by type, and the sensitivity analysis should compare both choices.

The third is that **items are treated as independent when they often are not**. Five photos of the same job score 0.86, more than one certificate (0.75). The cap of five items per skill limits how far this goes. Capping work photos per skill, or counting photos per job, would match the independence assumption better. These are exactly the questions `npm run confidence:sensitivity` should answer with numbers in the report.

### Module 3 is evaluated by properties, invariants and sensitivity, not accuracy

There is no ground truth for "is this worker really skilled", so Module 3 cannot report an accuracy score. The defensible evaluation has four parts:

- **Property tests** of the confidence function: more approved evidence never lowers the score, uncertainty falls as evidence grows, and self-claims alone never move it.
- **An invariant test:** no skill ever shows "Verified by evidence" without at least one approved evidence record behind it. This traceability is itself a claim an examiner can check.
- **A sensitivity analysis** of the weights.
- **A security test matrix** that maps each threat to the test that proves its mitigation. The prompt's Phase 5 list already covers GPS-stripped re-encoding, a renamed text file, PDF and HEIC rejection, 413 for oversize files, cross-worker access, and invalid transitions.

During testing, review turnaround time, approval and rejection rates by reason, and (if dHash is built) the share of duplicate flags that admins confirm can also be reported.

## Conclusion

Almost every defect in Modules 1 and 2 comes from one design habit: **the system treats an assertion as a fact.** A role typed into a form becomes an admin account. A query string becomes a database operator. A keyword becomes a trade. A keyword count becomes a percentage. An admin click becomes "Verified". The fixes in all three modules make the same shift, from asserted state to evidenced state. The server validates what arrives, the extractor suggests instead of writing, and verification is computed from reviewed, logged evidence instead of toggled. That shift is also what makes the project academically defensible. A system that records why it believes something can be measured, audited and explained in a viva in a way that an "AI" label cannot.

The practical order follows from this. The two actions that cannot wait are both outside the refactor: commit Module 2 to version control today, and start consented data collection this week, because neither can be compressed later. Next come the two-line hotfix for M1-1 and M1-2, if the live site holds real data, then the prompt's phases with this report's additions: a 15-character password rule or a written exception, server-side logout, `trust proxy`, strict query schemas, baselines and bootstrap intervals, and a non-deletable `suspected_fake` record. Every "confirmed" finding here rests on offline tests with fake models, so the first real Supertest run against mongodb-memory-server will be the true baseline. Its real output, not this report, is what should go into the FYP's test-case chapter.
